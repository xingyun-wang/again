## 五、教训（D-38 沉淀候选）

### 5.1 主教训：执行 `git mv` 类操作前先验证跟踪状态

**新增 D-43-X 候选规则**：

> **执行 git mv / git pull --rebase / rm-then-add 前，先 `git ls-files <target>` 验跟踪状态**。
> 未跟踪 → 不要 git mv；要么先 git add，要么 plain mv + git add。
> 1 行命令成本 = 杜绝一次 N-3 这种 spec 偏离。

证据：本次 N-3 `git mv` 直接报错才发现 plans/ untracked。本来 1 行 `git ls-files plans/` 就能提前发现。

### 5.2 次教训：决策室写 README ≠ 决策室已 git add

`plans/README.md` 明文要求 plans/ 必须 tracked，但写完当天没 add。说明决策室产出文档 ≠ 落地仓库状态 — 这与 D-39/D-41「落字未落地」同构（D-42 第 4 层）。

**D-43-X 候选规则（2）**：决策室产出新文档后，由下一个 subagent 在首次接触时做「git add + git ls-files 双向核对」并把核对结果回执。

### 5.3 决策室 spec 应包含「前置条件核对」步骤

N-3 task spec 包含「验证 ls / git status」，但没要求「`git ls-files plans/` 验跟踪」。如果加了，spec 阶段就会暴露 plans/ untracked 风险。
