### 1.1 ⭐ 中间那次 build 是**红的** —— 记下来，因为它是真 bug 被抓住的瞬间

第一次 build（我已改完 P2-1/P2-2/P2-4/P2-5 之后）**失败**：

```
#11 81.32 FAILED tests/api/v1/test_review_debt_p2.py::test_p2_4_delete_question_reclaims_question_image_file
#11 81.32 E           AssertionError: 题图文件还在磁盘上：/tmp/pytest-of-root/pytest-0/test_p2_4_delete_question_recl0/1/1/1.png
#11 81.32 E           assert not True
#11 81.32  +  where True = is_file()
#11 81.32 1 failed, 382 passed, 16 skipped, 4 warnings in 73.28s (0:01:13)
```

**根因（我自己的写法的错，不是台账写错）**：
我第一版 `delete_question` 写的是 `storage_paths = [row.storage_path for row in q.images if row.storage_path]`。
但 `Question.images` 是 `lazy="selectin"` 的**关系集合** ⇒ 首次访问就**加载并缓存**在 identity map 里；
而 fixture 的 session 是 `expire_on_commit=False` ⇒ 后续 commit **不刷新**它。
上传端点又是先 `db.get(Question, ...)`（此刻集合 = **空**）→ 再 `db.add(image)` 直插 `question_images` 行
（**不进集合**）⇒ 删题时读 `q.images` 拿到的是**陈旧的空集合** ⇒ `storage_paths` 为空 ⇒ 磁盘文件永远不删。

**修法**：改成**显式 query**（永远打 DB，拿真值），与 `delete_question_group` 一致：

```python
storage_paths = [
    row.storage_path
    for row in db.query(QuestionImage)
    .filter(QuestionImage.question_id == question_id)
    .all()
    if row.storage_path
]
```

> 这条留档的理由：**「关系集合是缓存」**这个坑不在台账上，是我这轮新踩的。
> 写清机制 ⇒ 下次谁再写 `q.images` 就能看见。

## 二、后端四条 P2 各自的修法（对账用）

### P2-1 · 删组只 unlink 组图，小题自己的图全留磁盘

- **位置**：`backend/app/api/v1/routers/academic.py` `delete_question_group`
- **改法**：删组前**同时**收两批 `storage_path` ——
  ① `QuestionImage.group_id == group.id`（组图）② `QuestionImage.question_id IN (组内小题 id 列表)`（小题题图）
  ⇒ DB commit 之后逐个 best-effort `Path.unlink(missing_ok=True)`。
- **为什么两批不重复**：`question_images` 有 XOR CHECK（`ck_question_images_owner_not_null`）⇒ group_id 侧与 question_id 侧**互斥**。
- **为什么不用 ORM de-associate**：题组删除继续用 `db.execute(delete(QuestionGroup).where(...))` 走 DB 级 `ON DELETE CASCADE`
  ⇒ 避免 ORM 把小题**移出组**（那会触发 `ck_question_images_owner_not_null`）。

### P2-2 · 500 响应体拼 `{e}` ⇒ 客户端能看到 SQL / 表名 / 约束名

- **放大器**：`backend/app/core/errors.py` — `detail` 被直接当 `message` 返回。
- **改法**：
  1. `core/errors.py` 新增固定文案常量：
     ```python
     INTERNAL_ERROR_MESSAGE = "服务暂时不可用，请稍后重试"
     ```
  2. **全部 5xx 站点**（18 处 `detail=INTERNAL_ERROR_MESSAGE`）改成只回这句；**原始异常细节只进服务端日志**（`logger.exception(...)`）。
  3. **额外收尾**（审计点名「条件泄漏」）：`TextbookUploadError` 里那条把**内部设计**（字段名 `extraction_source` + 规则号 D-37 + fail-closed 实现口径）
     透给客户端的文案 ⇒ 改为**日志留细节、客户端拿受控文案**。
  4. `textbook_upload.py` 里 9 处 `f"...：{e}"` ⇒ 改为受控文案 + `logger.exception` 留细节。
- **改前 vs 改后（真实对照）**：
  - 改前：`500` 的 body 是 `{"message": "DB write failed: psycopg2.errors.UniqueViolation: duplicate key value violates unique constraint \"ix_question_images_question_order\""}`
  - 改后：`{"message": "服务暂时不可用，请稍后重试"}`（细节只进 `app.api.v1.routers.academic` 的 ERROR 日志）
- **4xx 不动**（台账口径）：4xx 的 `detail` 是**业务信息**（如 409 删组时「题组含 N 道小题…」）⇒ 保留原样。
  改后残留的 6 处「异常对象文本进响应体」全部是**受控 4xx 业务文案**（`UploadValidationError` / `UploadTooLargeError` / `TextbookUploadError` / 业务 `ValueError`）⇒ 按台账口径保留。

### P2-4 · `delete_question` 只删行不 unlink 题图

- **位置**：`backend/app/api/v1/routers/academic.py` `delete_question`
- **改法**：`db.delete(q)` 前用**显式 query** 收 `storage_path`（见 §1.1 的根因说明）⇒ `db.commit()` 之后 unlink。
- **删失败不返 5xx**：unlink 抛 `OSError` ⇒ 只 `logger.warning` 记「孤儿文件」⇒ 不影响删除本身的成功语义。

### P2-5 · `MAX_QUESTION_IMAGE_BYTES` 被组图复用

- **改法**：拆成**两个独立常量**（各 5MB，值相同但**不是彼此的别名**）：
  ```python
  MAX_QUESTION_IMAGE_BYTES = 5 * 1024 * 1024   # 单题题图
  MAX_GROUP_IMAGE_BYTES   = 5 * 1024 * 1024   # 题组材料图
  ```
  组材料图上传流改用 `MAX_GROUP_IMAGE_BYTES` ⇒ 将来单独调其中一个**不会误伤**另一个。
- **当前无功能差异**（台账原文：「当前无功能缺陷，行为正确；风险在未来」）⇒ 本条是**为将来拆雷**。

## 三、前端：两处欠账

### P2 · 内联建题成功后不刷新列表（数据已落库，列表看不到）

**星轨给的 A/B 两种修法我都没照抄**（OUTBOX #7 硬约束 1 明确允许第三种，但要说明为什么）。

- **A（星轨推荐）**：内联建题 / 编辑 / 删除成功后调 `onSaved?.()`。
- **B**：`onClose` 里也 `refreshAll()`。
- **我选的第三种**：**凡是改变了服务端数据的动作，一律通知列表页** ⇒ 在 **建组** + **内联建题** + **内联编辑小题** + **内联删小题** 四处调 `onSaved?.()`。

**为什么不只做 A**：星轨描述的**现象**是「新建题组 → 内联建 3 道小题 → 点取消 → **列表页看不到这个组**」。
但**建组那一步**（`handleCreate` → `POST /question-groups`）同样落了库、同样**不通知列表页** ⇒
只按 A 修（只管内联建题）的话，「建组后不建题直接关闭」仍会造出**看不见的组**
⇒ 用户以为没建成 ⇒ 重做一遍 ⇒ **产生重复题组** —— 正是星轨担心的那条风险。
⇒ 按**语义**修（数据变了就通知），而不是按**位置**修。

**改动面**：`frontend/src/components/QuestionGroupDrawer.tsx`（**+10 行 / 4 处 `onSaved?.()`**）
· `frontend/src/api/questionGroups.ts` · `frontend/src/pages/Questions.tsx`（P3 用）

### P3 · 删组确认框把后端技术参数透给用户

- **现象**（星轨实测）：确认框原文含 `确认删除请加 ?force=true` ⇒ 老师看不懂、还暴露内部调用细节。
- **改法**：**前端展示层裁剪**，后端 message **不改**（后端 message 对 API 调用方是有用信息；
  改后端会破坏既有契约 —— `backend/tests/api/v1/test_question_groups.py:435` 断言 `force=true` 在 message 里）。
- **裁剪函数**（`frontend/src/api/questionGroups.ts:142` `toUserFacingDeleteHint`）：
  - 只在「分号后半句**确实含 force 指引**」时才裁 ⇒ 后端以后改措辞**不会**把「用户在删什么」那半句也误裁掉。
  - 前半句「题组含 N 道小题、M 张材料图、K 个材料块」**原样保留**。
- **改动面**：`frontend/src/api/questionGroups.ts`（+25）· `frontend/src/pages/Questions.tsx`（+8/−4）
