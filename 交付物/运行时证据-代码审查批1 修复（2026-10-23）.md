## §1 P1-1 修复内容

### 1.1 加了一道归属校验 —— **L2**

新函数 `backend/app/api/v1/routers/academic.py:1954` `_check_group_image_ownership`：

```python
image_ids = {b.image_id for b in blocks if b.image_id is not None}
if not image_ids:
    return
rows = (
    db.query(QuestionImage.id)
    .filter(
        QuestionImage.id.in_(image_ids),
        QuestionImage.group_id == group.id,
    )
    .all()
)
owned = {row[0] for row in rows}
missing = sorted(image_ids - owned)
if missing:
    raise HTTPException(
        status_code=422,
        detail=f"image_id 不属于本题组：{missing}",
    )
```

**三个口径，都是我核源后定的，不是照抄审查意见**：

1. ⭐ **比对 `group_id == group.id`，不看 `block_type`** ——
   星轨的建议是「对每个 `block_type=='image'` 的 `image_id` 做校验」。
   **我扩大了范围**：FK CASCADE 挂在 `content_blocks.image_id` 上，
   **任何**带 `image_id` 的块都会被图删除连带带走 ⇒
   校验必须覆盖**全部**带 `image_id` 的块，不只是 image 块。
   （否则 `block_type="text"` + 别人的 `image_id` 这条路还开着。）

2. ⭐ **同一条 SQL 顺手挡住「填题图」** —— 题图的 `group_id` 是 NULL（XOR CHECK 保证
   `question_id` 与 `group_id` 互斥）⇒ `NULL == group.id` 不成立 ⇒ 题图压根进不来。

3. ⭐ **「不存在」与「不属于本题组」同码同文案**（都是 422 + 同一句
   `image_id 不属于本题组：[...]`）⇒ 不给「这个 id 存不存在」的探测信号。
   与读端点的「404 不泄露存在性」口径一致。

### 1.2 ⭐ 校验**先于删除**（这是我核源时发现并补的一层）

`_replace_group_blocks` 原本的顺序是「**先删旧块** → 再写新块」。
若把校验放在删除之后 ⇒ 校验不过时旧块**已经被删掉** ⇒ **那是数据破坏，不是校验失败**。

⇒ 校验提到删除之前。

### 1.3 ⭐⭐ 顺带发现：PUT 的写入顺序也会留半截状态

核 PUT 处理器时发现它的写入顺序是
`difficulty → knowledge_point_ids → blocks`，**每步都 `db.flush()`**。
若 blocks 的校验放在最后一步才跑，422 抛出时 difficulty 与 KP 关联**已经被 flush**：

- 生产：`get_db` 的 `finally → db.close()` 会回滚未提交事务 ⇒ **侥幸没事**；
- 测试：`mock_db_session` 是**共享会话**（fixture 与 API 用同一个），
  `close` 不会发生 ⇒ **半截状态留在会话里污染后续断言**。

⇒ **改成两阶段**：阶段 1 全部校验（KP 归属 + image_id 归属），阶段 2 统一应用。
⇒ 422 时事务里**零写入**。

**守卫有两道，是故意的**（都是可执行断言，不是注释）：
- `:2015` —— `_replace_group_blocks` 内部（**唯一写入口**，必须自带守卫）；
- `:2206` —— PUT 处理器阶段 1（保证 422 时前面没有半截写入）。
