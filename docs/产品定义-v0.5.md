## 0. 产品灵魂（最重要）✅ 定稿

> 我们要做的产品是一个平台，该平台为老师主导的教学闭环操作系统，深度嵌入教学环节。

---

## 1. 目标用户 ✅ 定稿

- 王星云（析木高中地理老师）
- 班级规模：单班 50 人
- 学科范围（MVP）：仅限地理学科
- 角色：任课教师

> **数据模型预决策（载曜建议 A，已采纳）**：MVP 阶段数据模型预留学段字段
> - `Student.grade_level` (enum: junior_high / senior_high)
> - `Question.applicable_grades` (multi-select)
> - `Class.grade_level` (enum)
>
> MVP 阶段几乎都填 `senior_high`，Phase 2 加学段时无需回填。

### 1.2 用户扩展路径

| 阶段 | 范围 | 触发 |
|---|---|---|
| **MVP** | 星云 + 自己班级（高中地理） | — |
| **全学段小范围** | 星云（高中地理）+ 1 初中地理老师（**最小验证集合 = 2 人**，载曜建议 B） | 星云自己班级实验验证通过 |
| **跨学科小范围** | + 其他学科同事 | 全学段验证通过 |
| **单校多学科** | 单校全员老师 | 跨学科验证通过 |
| **多校** | 多校老师 | 单校验证通过 |

> **关于顺序**：
> - 全学段 in Phase 2（MVP 验证通过后立即开始）
> - **多学段 before 多校**（先内部矩阵验证，再规模复制）
> - 你亲自答的 5 阶段路径

### 1.3 学生 / 家长角色

- **核心**：学生学习画像（MVP 不构建，**数据模型预留**）
- **呈现**：家长端 + 学生端 = 两种呈现方式
- **MVP 范围**：专注教师端，深度嵌入工作流
- **家长 / 学生开放**：等迭代（不在 MVP）

### 1.4 用户 / 数据边界

- **学科之间**：**学科独立**——每个学科老师有独立的题库 / 学情 / 备课空间，互相看不见
- **同学科跨学段**：**也独立**——初中地理 / 高中地理完全分开
- **核心原则**：**题库属于教师个人资产，他人无法访问**；未来共享题库 = 教师**主动选择上传**（共建题库愿景）

> **§1.4 注**：此原则**传染 §3 / §7 / §9**——走到那三节直接引用 §1.4，不重新发明

### 1.5 操作员角色（非用户）

- **教务处**：负责学生答题卡上传
  - **MVP 阶段**：星云代劳（不需独立账号）
  - **迭代阶段**：由专人负责（独立账号 / 权限）
- 其他操作员角色（系统管理员 / 技术支持等）待 §X 识别

## 2. 核心场景（用户故事）✅ 定稿

> 闭环是产品的灵魂，深刻嵌入教师工作流形成闭环是产品生命力所在。

### 2.2 MVP 闭环 4 步

**步骤 1 · 备课**
- 教师上课前登录平台
- 输入：学科知识库（系统提前录入；内容广泛：教参 / 教科书 / 课标 / 教学计划 / 课节时长 / 教学形式 / 校本内容等）+ 系统储存的学生学情画像
- 通过 AI 综合处理
- 输出：**授课建议**给教师

**步骤 2 · 出作业**
- 教师课后登录
- 来源：自建题库 + 外部题库（具体来源见 §3）
- 差异化规则：4 等级（档位定义见 §1.4 / §3），难度不同，同等级内容不同
- 形式：纸质版分发给学生
- 系统：储存学生答案，等待答题卡上传

**步骤 3 · 上传 + 评分**
- 学生上交作业（标准答题卡）
- 学校**教务处（操作员）**上传各年级 / 班级 / 学科的标准答题卡内容
  - **MVP**：星云代劳
  - **迭代**：专人负责
- 系统评分（选择题 / OMR 读卡机；主观题 = 教师批阅 + 手动评分）
- 教师确认评分

**步骤 4 · 学情画像形成 + 再备课**
- 系统根据学生长时间表现刻画学情画像（学生 / 班级 / 学科三维度）
- 提供给任课教师
- 教师根据系统反馈和建议进行备课
- **闭环形成**

### 2.3 老师使用节奏

> **几乎每日登录**——从 §2.2 4 步骤推导：备课 / 出作业 / 评分 / 再备课 每一步都涉及登录

（§2.3 是结论，不是用户直接说的——用户 Q3 是让我从 §2.2 推导使用频率，已验证推导一致）

### 2.4 多角色画像（远期）

| 角色 | 看到的画像 | 时机 |
|---|---|---|
| 任课教师 | 学生 / 班级 / 学科 学情 | MVP |
| 校级领导 | 教师画像 | 迭代 |
| 教育主管部门 | 学校画像 | 迭代 |
| 教研领导 | 学科画像 | 迭代 |
| 学生 | AI 学情画像（自己的） | 迭代 |
| 家长 | AI 学情画像（孩子的） | 迭代 |

> **§2.4 注**：多角色画像超出 §1 MVP 范围——但行性数据架构上需要预留（详见 §1.3 / §8）。

## 3. 功能 1：差异化作业 ✅ 定稿

### 3.1 差异化维度

- **MVP**：仅**能力分层**（4 等级）
- **Phase 2**：兴趣主题（情境化）
- **不做**：学习风格

### 3.2 档位

- **字母升序 = 难度升序**：D 基础 / C 进阶 / B 挑战 / A 扩展
- **档位数**：4
- **同档**：难度相近，**题目不同**（避免抄答案）
- **动态调整**：K=5 / M=4（升档）+ N=3（降档）
- **老师手动覆盖**：可调整个别学生档位
- **初始档位**：老师手动设定
- **触发场景**：老师主动触发

### 3.3 题目来源

- **老师自建题库**（个人资产，§1.4 原则）
- **外部题库**：菁优网 / 学科网 / 其他
- **AI 出题**：**MVP 绝不碰**——MVP 阶段不让 AI 出任何题目；迭代阶段再考虑

### 3.4 题目类型 + 输出

- **题目类型**：按教师需要（不限制——选择 / 填空 / 主观题都可）
- **各题型数量**：按教师需要
- **输出**：**PDF，每生一份**
- **打印下发**：教务处（操作员，§1.5）
- **主观题批阅**：教师手动批阅 + 手动录分（UI 必须可用）

### 3.5 反马太效应

- **D 档作业强制 20% 拔高**（从 C/B 档题池抽题）
- 避免后进生自我放弃

### 3.6 老师审阅流程

1. 老师登录 → 选择章节 / 知识点 / 档位 / 题量
2. 作业生成引擎 → 按档位差异化组合
3. 老师审阅 → 修改 → 导出 PDF
4. 教务处打印 → 下发学生

## 4. 功能 2：学情反馈 → 备课建议 ✅ 定稿

### 4.1 学情数据模型（三维度）

- **学生**：当前档位 / 档位历史 / 知识点掌握度向量 / 作业记录 / 异常标记
- **班级**：整体知识点掌握度 / 整体档位分布 / 班级趋势
- **学科**：跨班级汇总数据（Phase 2+ 显示威力，MVP 近似 = 班级画像）

### 4.2 学情数据来源

| 数据 | 来源 | MVP 状态 |
|---|---|---|
| 选择题作答 | OMR 读卡机 | ✅ MVP 主路径 |
| 主观题分数 | 老师手动录分 | ✅ MVP 必须 |
| 知识点掌握度 | 系统聚合 | ✅ MVP |
| 档位历史 | 系统自动记录 | ✅ MVP |
| 作业完成率 | 系统记录（交/未交） | ✅ MVP |
| 完成时长 | 系统计时 | ⏳ MVP 不强制 |

### 4.3 备课建议三层

| 层级 | 频率 | 内容 |
|---|---|---|
| **微观**：下节课讲什么 | 每日 | "本节课建议讲 X；Y 知识点有 60% 学生错，可复盘；Z 知识点全员掌握，可跳过" |
| **中观**：本周重难点 | 每周 | "本周建议重点：① X ② Y；典型盲点：Z；可略过：W" |
| **宏观**：班级整体改进方向 | 每周 | "班级最近 2 周 X 知识点持续薄弱；建议用 PQR 方法改进" |

### 4.4 重点关注学生清单

| 类型 | 触发条件 |
|---|---|
| 后进生 | 档位持续 D 档 / 连续退步 / 多知识点未掌握 |
| 进步大 | 最近 N 次档位上升 ≥ 1 档 |
| 退步大 | 最近 N 次档位下降 ≥ 1 档 |
| 波动大 | 档位反复升降 |
| 其他（学习成绩异常波动）| 系统检测到异常 |
| 优等生 | MVP 不特别关注 |

### 4.5 数据冷启动期

- **冷启动期 = 5-10 课时**
- **反馈标注置信度**："基于 X 次作业的初步判断，置信度较低"
- **UI 明确提示**，避免老师依据不完整数据做决策

## 5. 功能 3：AI 备课助手 ✅ 定稿

### 5.1 输入范围

- 学科知识库（系统提前录入，详见 §5.3）
- 学情画像（§4）

### 5.2 输出范围（MVP 极简）

- **重点 / 难点 / 授课建议**
（不扩展：引入案例 / 讲解顺序 / 板书设计——MVP 保持极简）

### 5.3 学科知识库录入

#### 5.3.1 范围（人教版 / 全 5 册）

| 册 | 名称 |
|---|---|
| 1 | 必修第一册 |
| 2 | 必修第二册 |
| 3 | 选择性必修 1 |
| 4 | 选择性必修 2 |
| 5 | 选择性必修 3 |

#### 5.3.2 录入策略：**分阶段录**

| 章节类型 | 录入深度 | MVP 状态 |
|---|---|---|
| **本学期要教的章节** | **精录**：完整结构（标题 / 关键概念 / 教学顺序 / 重点 / 难点 / 教学建议） | ✅ MVP 上线前完成 |
| **其他章节** | **粗录**：仅大纲（标题 / 主要知识点 / 关键概念） | ⏳ MVP 不必，后期补录 |

> **学期迭代**：每学期开课前扩展本学期精录范围

#### 5.3.3 录入者

- **MVP**：星云一人
- **Phase 2+**：教研领导接手

#### 5.3.4 来源

- 纸质书电子版（PDF）
- 网上教学参考（优先级：**新课标 / 教参** > **重点高中教案** > 个人博客 / 商业机构）

#### 5.3.5 LLM 选型 + AI 辅助录入

- **LLM**：DeepSeek-V3（沿用 v0.4；性价比高 + 中文强；如有更优选择再评估）
- **AI 辅助录入**：用 LLM 预提取 PDF 结构化信息，星云**审阅 + 编辑**——省 50%+ 工作量
  - **不违反 §3.3**：AI 是「数据提取」不是「内容生成」

#### 5.3.6 录入时机

- MVP 上线前：本学期章节**精录完**
- 其他章节：**粗录**后边用边录
- 学期迭代：每学期开课前扩展本学期精录范围

### 5.4 MVP 边界

- AI 输出 = **建议**，老师必须审阅（沿用 §7 合规 + v0.4「教师最终审阅流程」）
- 老师审阅后用于实际备课

### 5.5 与 §3.3 边界（重要）

- **§3.3 禁用**：AI 生成新题目（AI 出题）
- **§5.1-5.4 允许**：AI 综合学科知识库 + 学情 → 输出授课建议（AI 综合分析）
- **§5.3.5 允许**：AI 辅助录入（数据提取，人在回路）
- 这三者本质不同：AI 出题 = 生成内容；AI 备课 = 综合数据；AI 录入 = 数据提取（人在回路）

## 6. 数据采集 ✅ 定稿

> **最后更新**：2026-09-15

### 6.1 采集路径
- **MVP 主路径**：OMR 读卡机 + 系统标准答题卡
- **备用**：手机拍照 OCR 接口预留，**MVP 不做 UI**
- 强拍板：MVP 只走 OMR 一条路，先跑起来；OCR 未来需要再启

### 6.2 答题卡格式
- **MVP**：系统提供标准模板，统一印刷
- 模板字段：姓名 / 学号 / 班级 / 学科 / 章节 / 档位 + 题目作答区（选择 / 填空 / 主观）
- 限制老师自由，但 MVP 工程量可控

### 6.3 评分流程
- **选择题**：OMR 自动评分
- **主观题**：教师手动批阅 + **按学生顺序手动录分 UI（MVP 极简）**
- 50 人班级逐个录分 MVP 阶段可控

### 6.4 MVP 前置依赖（最大 blocker）
- **至少 1 款扫描仪实测验证（TWAIN 接口兼容）**
- 这是 §6 真正的 blocker——MVP 启动前必过
- 不验证不准上线

### 6.5 数据存储 + 隐私
- **本地为主**（学校服务器）
- **云端备份**（阿里云 OSS），上传前脱敏
- 符合 CHARTER §6 合规

### 6.6 与 §2.2 闭环步骤 3 的关系
- §2.2 步骤 3 = 「上传 + 评分」
- §6 是 §2.2 步骤 3 的工程细化

## 7. 合规边界 ✅ 定稿

> **最后更新**：2026-09-15
> **原则**：CHARTER §6 合规边界 5+4 条不变；§7 是 MVP 工程细化。

### 7.1 家长授权机制
- **MVP**：一次性授权（入职时签字），覆盖全部使用期
- **迭代阶段**：评估是否升级为「年度授权」或「每次作业前授权」
- 涉及 14 岁以下学生必须先授权才能使用

### 7.2 数据脱敏范围（分级）
**本地**（不离开学校服务器）：
- 姓名 / 学号 / 联系方式 / 家庭住址
- 学生身份证号等敏感 PII

**云端**（脱敏后）：
- 档位 / 知识点掌握度向量 / 作业记录
- 班级聚合画像（去个人标识）

**云端备份**：阿里云 OSS，上传前脱敏 + 加密（符合 CHARTER §6）

### 7.3 未成年人「钢铁模式」（分层）
| 学段 | 模式 | 老师权限 |
|---|---|---|
| **小学** | **强制开启（关不掉）** | 不可关闭 |
| **初中** | **默认开启** | 可手动关闭（需理由） |
| **高中** | **默认开启** | 可关闭（无理由） |

**MVP 重点**：MVP 主要是高中（星云本人）；初中 / 小学实现等迭代

**钢铁模式具体内容**：
- 禁用 AI 直接给学生反馈
- 禁用学生间数据共享
- 禁用个性化推荐
- 学习画像只在教师端显示

### 7.4 AI 生成内容声明（UI 标签）
**MVP UI 必须显示**：
- 学情画像页：标签「本画像含 AI 综合分析」
- AI 备课助手输出：标签「本建议由 AI 生成，需教师审阅」
- **不标记**：OMR 自动评分（纯算法）/ 老师手动录分 / 系统聚合数据

### 7.5 教师最终审阅流程（流程节点硬约束）
**MVP 系统流程硬约束**：
- **作业生成后**：必须审阅才能导出 PDF（§3.6 流程节点 3）
- **学情画像生成后**：老师必须点确认才能纳入下次备课建议（§4.3）
- **AI 备课建议生成后**：必须审阅才能用于实际备课（§5.4）

**UI 设计**：每个流程节点显示「老师审阅状态」标记（已审 / 未审 / 已修改）

### 7.6 与 §2.2 闭环的关系
- §2.2 步骤 3（上传 + 评分）的合规约束：教师最终审阅（§7.5）
- §2.2 步骤 4（学情画像 + 再备课）的合规约束：AI 声明（§7.4）+ 教师审阅（§7.5）
- 全闭环都有合规约束覆盖

## 8. MVP 范围 / 平台最终覆盖 ✅ 定稿

> **最后更新**：2026-09-15

### 8.1 平台最终覆盖
- 初中 / 高中 **全学段全学科**
- 同学科跨学段独立（§3.3 CHARTER 硬约束）

### 8.2 MVP 起点
- **教师**：王星云本人（高中地理老师）
- **学科**：高中地理（不锁年级）
- **班级规模**：单班 50 人默认，**后端可配**，UI 按 50 优化

### 8.3 MVP 周期
- **不必设周期**——MVP 迭代推进，不锁 8 周或 6 周
- **里程碑**（§10 排期细化）：MVP 上线 → 星云验证 → 全学段扩展
- MVP 时间不是承诺，是规划

### 8.4 MVP 关键路径（端到端验证）
- MVP **必须跑通 §2.2 4 步闭环**：
  1. 备课（AI 备课助手 + 学科知识库）
  2. 出作业（差异化作业 + 系统标准答题卡）
  3. 上传 + 评分（OMR 主路径 + 按学生顺序手动录分）
  4. 学情画像 + 再备课（学情画像 + AI 备课迭代）
- **教学闭环是产品灵魂**（§0 沿用）——MVP 必须端到端

### 8.5 MVP 试用启动条件
- **MVP 上线 + 星云本人先跑 1 班验证**——验证通过再扩展到 §1.2 全学段
- 验证不通过：迭代修复，不进入下一阶段

### 8.6 MVP 设备清单（学校采购）

## 9. 技术选型 ✅ 定稿

> **最后更新**：2026-09-15
> **原则**：MVP 选型要看 Phase 2 / Phase 3 扩展性，**不能阻碍前路**（大区域 / 全学段 / 全学科）

### 9.1 前端栈
- **React 18 + TypeScript + Vite + Ant Design 5**
- 通用栈，Ant Design 5 国内生态成熟

### 9.2 后端栈
- **Python 3.11 + FastAPI + Celery**
- MVP 阶段只用 FastAPI 同步 API
- Celery 依赖保留，Phase 2 多区域时启用分布式任务队列

### 9.3 数据库
- **PostgreSQL 15（开发 + 生产都用）**
- MVP 用 Docker Compose 一键起 PG
- **不用 SQLite 避免 Phase 2 数据迁移**

### 9.4 LLM 选型
- **DeepSeek-V3 + Provider 抽象层**
- MVP 用 DeepSeek-V3（沿用 v0.5 §5.3.5）
- 实现 `LLMProvider` 接口（`chat()` / `embedding()`）
- 数据出境：MVP 用 DeepSeek 国内 API；Phase 2 多区域按区域选 Provider

### 9.5 部署方案
- **Docker Compose 单机 MVP + 无状态 FastAPI**
- MVP 单机：`docker-compose up -d`（PG + FastAPI + nginx）
- 无状态 = session / 文件上传走 DB / OSS，不存内存
- Phase 2 横向扩展（k8s / 多实例）零成本

### 9.6 关键架构决策（避免未来重构）
| 决策 | 目的 |
|---|---|
| 无状态 FastAPI | 横向扩展零成本 |
| LLM Provider 抽象 | 多模型切换零重构 |
| 数据模型预留学段 / 学科字段 | v0.5 §1 已锁 |
| Docker Compose 起 PG | 不用 SQLite 避免迁移 |
| Celery 依赖保留 | 分布式任务队列预留 |
| OSS 对象存储抽象 | MVP 本地文件夹实现；多区域可切阿里云 / AWS / 自建 |
