## 7. 协作与灾难恢复

### 7.0 协作分工 + 审写分离（2026-10-20 修订；「≥20 行必派 subagent」阈值已废止）

> **修订依据**：星轨《裁决 — 决策室规则修订：以「审写分离」取代「行数阈值》》（裁决人：星轨 / 流程与成果审查；批准：星云 2026-10-20 14:36）
> **处置对象**：D-43 §5（决策室不修代码逻辑 / ≥20 行 / 需 push+CI 必派 subagent）—— **阈值部分已废止**（留痕见 `docs/decisions.md` D-43 + `notes/milestones.md` §治理.13）
> **一句话**：**谁写代码不重要，谁审、拿什么验才重要。**

- **决策室** = 星云（需求方 / 拍板）+ 星轨（审查方 / 流程与成果审查）：方向 + 拍板 + 审查 + 验收
- **实施方 = 载曜**：写前后端 / 跑命令 / debug —— **在主会话还是 subagent 都可**，看上下文代价（止损 1），**不再按行数划线**
- **审查方 ≠ 实施方**（红线 1）：载曜不得自审自批自己的产出

**为什么废除阈值**：旧规则用「行数」代理「风险」，而两者几乎不相关。2026-10-20 当日 5 笔实施全部由载曜直接完成（合计约 700 行），复核发现 4 个问题——

| # | 问题 | 严重度 | 强制派 subagent 能否提前发现 |
|---|---|---|---|
| 1 | 知识点多选筛选静默失效（axios 数组序列化成 `kp[]=`，FastAPI 只认重复键） | P0 | 不能（subagent 同样只跑 lint/build）|
| 2 | 前端新 + 后端旧 → 题库页整页白屏（`#root` = 0） | P0 | 不能（部署组合问题，CI 里不存在该组合）|
| 3 | 前端对可选展示字段零防御（缺一个字段就崩整页） | P1 | 不能（设计取舍）|
| 4 | 选教材时对全部章节逐个发请求（N 个） | P2 | 不能（实现选择）|

四个问题**全部靠「真浏览器点一遍」发现**，没有一个靠「换谁写代码」能避免；而强制派 subagent 的代价（两层上下文重建与交接）质量零提升，反而是当日失真（派工单漏项 / 状态过期 / 证据缺失）的来源。

#### 红线 1 · 写的人不审自己的东西

- 实施方**不得自行宣布「通过验收」**。只能报三样：**改了什么 / 跑了什么命令 / 结果是什么**。
- **验收判据不得由实施方单独定稿**。brief / DoD 必须由**审查方落字**并经**需求方确认**后才开工。
  - ⚠️ 2026-10-20 当日最大教训：1b 的 brief 由载曜自写自批（11:46 入仓、12:00 代码写完）⇒ 判据未经确认 + 后续 P1 未被设计时考虑。
- 出问题时的顺序：**先判根因，再报**；不得把「测试通过」当作「功能正确」的证明。

#### 红线 2 · 前端 / UI / 部署相关改动必须挂运行时证据

- 判据：必须在**真实浏览器**里操作过（点击、输入、翻页），并留下可核对的记录（**请求 URL 原文**、截图、控制台错误）。
- **静态三查（读代码 / tsc / build）不算证据；CI 绿也不算** —— CI 里没有浏览器。
- 谁做不限，但**必须有人做**。载曜无浏览器工具 ⇒ 由**星轨用 Playwright + 系统 Edge** 执行；载曜在交付里**显式声明「运行时验收待星轨执行」并把验收点列清**。
- **禁止用「等价证据」替代页面证据**。等价证据可说明实现正确性（如加载真实源码验证 URL 序列化），但**不能替代页面可用性**。

#### 止损 1 · 按上下文代价决定是否派 subagent，不看行数

| 情形 | 做法 |
|---|---|
| 需要跨 5 个以上文件摸索、找根因、探查未知 | 派 subagent（价值 = 节省主上下文）|
| 目标明确、改动范围已界定 | 直接做 |

行数不作判据：**20 行可能致命**（改一个判断条件），**500 行可能纯搬运**。

#### 止损 2 · 大改动手前先出计划

单次改动**预期 >300 行或跨 >5 个文件** ⇒ 动手前先出 3~5 行计划（**改什么 / 不改什么 / 怎么验**），发给审查方，**等到一句「可以」再动手**。

例外：CI 红、线上故障等紧急修复可先做后补，但交付时必须**主动标注「跳过了预案」**。

#### 没有变的部分（一并抄进宪法）

1. **push 授权**：commit msg 含 `[origin-push]` 才可推 origin；**推 github 须星云单独批**。
2. **报绿必须带 CI run 号 + commit SHA**，不许只说「测试通过」。
3. **不许为了让验收通过而修改验收标准**。**砍范围可以，砍标准不行。**
4. **交付格式**：commit SHA + message、改动文件清单、命令结果、是否已推、是否需要新迁移、遇到的问题清单（含自己拍的决定）。
5. **不越界**：不动其他工单的代码范围，**不改后端契约去迁就前端**。

#### 交付前自查清单（载曜每次交付前过一遍）

- [ ] 我没有宣布「通过验收」，只报了「改了 + 跑了什么 + 结果」
- [ ] 验收判据是审查方落字的，不是我一个人定的
- [ ] 这是 UI / 前端 / 部署相关改动 ⇒ 我已声明「运行时验收待星轨执行」并列出验收点
- [ ] 改前预估 >300 行或 >5 文件？是的话，计划发过并拿到「可以」了
- [ ] commit msg 标了 `[origin-push]`；没有未获批准就推 github
- [ ] 没有为了过关去改标准、改判据、改测试断言
- [ ] 报「绿」时附了 CI run 号 + commit

### 7.6 工程推进分阶段 + 每段验收（项目级硬规则，D-25 + D-36-A/B/C + D-42）

每次工程推进（M0-M7 / 任何 sub-project）必须：

1. **分阶段**：每个 phase / 阶段独立可交付
2. **每段验收**：明确的验收门槛（具体指标，可验证）
3. **通过才能进下一阶段**：任何一条不达标 = 不进
4. **工程质量贯穿**：代码的健壮性 + 可维护性 是底线，不可妥协
5. **审查材料三锚齐全**（D-36-A/B/C + D-42）：
   - **D-36-A 环境钉死**：commit SHA + 镜像 digest + PG 版本 + 依赖锁文件 hash
   - **D-36-B 证据优先级**：机器证据 > 人工转录 > 口述；人工转录是 D-36 要消灭的对象
   - **D-36-C 降级声明**：CI 跑不动时显式标「静态审查」+ 不得用于清 P0

**实施**：
- 每个 subagent 任务 brief 必须含「验收门槛」段 + 「D-36-A/B/C 三锚齐全」声明
- 验收门槛必须可验证（自动化测试 / 命令输出 / curl 等具体指标）
- 不允许「省验收」——哪怕一个 sub-phase 也要有验收门槛
- 不允许「赶进度」——跳过验收 = 工程质量崩塌
- fail-open 三层复发（代码 / 部署 / 运维）触发 §7.0 例外条款收紧：跨层复用 = 强制升级流程审查（D-42 失败模式防护三原则）

**与 §7.0 关系**：§7.0 解决「决策室 vs 实施方」分工 + **审写分离**（2026-10-20 修订）；§7.6 解决「工地内部推进节奏」+ 「审查材料硬要求」。两者都是工程质量底线。

**未来警惕**：
- 「通过才能进下一阶段」是底线，不是建议
- 任何「省验收」或「赶进度」都是反模式，载曜主动拦截
- fail-open 复发 = 不是 bug 是结构（D-42）——打地鼠式修无效，必须建三原则护栏
